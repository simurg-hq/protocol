# Ping protocol, version 1

Status: draft. This document defines how a client reports a job run over
HTTP and the event a receiver emits for each accepted ping.

The key words MUST, MUST NOT, SHOULD and MAY are used as described in
RFC 2119.

## Roles

- **Client**: anything that sends pings: `curl`, the official CLI, an SDK.
- **Receiver**: the HTTP service that accepts pings. It validates the request,
  hands an event to the event consumer and responds. It does not interpret
  runs or monitor state.
- **Event consumer**: the service that reads events, verifies monitors, opens
  and closes runs and moves monitors between states.

## Principles

- A ping MUST never fail or slow down the client's job. Clients SHOULD use a
  short timeout and ignore errors.
- The ping URL is the credential (secret URL model). There is no other
  authentication.
- The receiver does not reveal whether a monitor exists. A well-formed ping
  is accepted even if the receiver cannot find its monitor.
- Version 1 changes are additive only. A breaking change needs a new version.

## Identifiers

| Name | Format | Regex |
| --- | --- | --- |
| Token | 128 random bits, RFC 4648 base32, lowercase alphabet `a-z2-7`, no padding, 26 characters | `^[a-z2-7]{26}$` |
| Project key | `pk_` followed by 26 base32 characters as above | `^pk_[a-z2-7]{26}$` |
| Slug | Lowercase letters, digits and `-`, 1–64 characters, starting with a letter or digit | `^[a-z0-9][a-z0-9-]{0,63}$` |
| Run ID | ULID (26 characters, Crockford base32) | `^[0-7][0-9A-HJKMNP-TV-Z]{25}$` |

The receiver checks tokens, project keys and slugs against these regexes
only; it does not decode them. Run IDs are generated by the receiver. In requests they are matched
case-insensitively and always returned and emitted in upper case.

## Endpoints

All endpoints live under `/ping/`. A monitor is addressed either by its
token or by its project key and slug.

| Path | Kind | Meaning |
| --- | --- | --- |
| `/ping/{token}` | `success` | The run finished successfully. |
| `/ping/{token}/start` | `start` | A run started. |
| `/ping/{token}/fail` | `fail` | The run failed. |
| `/ping/{token}/{exit_code}` | `exit` | The run finished with this exit code. |
| `/ping/{project_key}/{slug}` | `success` | As above, addressed by slug. |
| `/ping/{project_key}/{slug}/start` | `start` | |
| `/ping/{project_key}/{slug}/fail` | `fail` | |
| `/ping/{project_key}/{slug}/{exit_code}` | `exit` | |

### Path grammar

```abnf
ping-path    = "/ping/" target [ "/" action ]
target       = token / project-key "/" slug
action       = "start" / "fail" / exit-code
exit-code    = "0" / ( %x31-39 *2DIGIT )   ; 0-255, no leading zeros
```

Resolution rules:

1. If the first segment after `/ping/` starts with `pk_`, the request uses
   slug addressing and the second segment is always the slug. A slug named
   `start`, `fail` or `42` is therefore unambiguous: `/ping/{project_key}/start`
   is a success ping for the monitor with slug `start`.
2. Otherwise the first segment MUST be a token, and the second segment, if
   present, is the action.
3. Exit codes are decimal integers from 0 to 255 without leading zeros.
   Exit code 0 means success; 1–255 mean failure.
4. Paths are matched exactly and are case-sensitive. A trailing slash, an
   empty segment, an extra segment or any segment that does not match the
   grammar makes the path malformed.

### Query parameters

| Parameter | Applies to | Meaning |
| --- | --- | --- |
| `rid` | `success`, `fail`, `exit` | Run ID returned by `start`. The finish ping closes that run. Without `rid` it closes the most recent open run of the monitor. |
| `create` | Slug addressing | `create=1` asks the event consumer to create the monitor if the slug does not exist yet. Any other value means no. |

`rid` on a `start` ping is ignored in version 1. `create` with token
addressing is ignored. Unknown query parameters are ignored.

### Methods

`GET`, `POST` and `HEAD` are accepted on every endpoint and have the same
meaning. Only `POST` may carry a body. Any other method gets `405` with an
`Allow: GET, HEAD, POST` header.

### Headers

| Header | Direction | Meaning |
| --- | --- | --- |
| `User-Agent` | Request | Determines the event `source` (see below). |
| `Idempotency-Key` | Request | Optional. 1–128 printable ASCII characters (`%x21-7E`). A retry of the same ping SHOULD reuse the key. The receiver passes it on; duplicate detection is the event consumer's job. |
| `Content-Type` | Request | `application/json` selects JSON body parsing; anything else is treated as text. |
| `Run-Id` | Response | Run ID of the run opened by a `start` ping. |
| `Retry-After` | Response | Seconds to wait, sent with `429` and `503`. |

`source` is derived from `User-Agent`:

| User-Agent starts with | `source` |
| --- | --- |
| `simurg-cli/` | `cli` |
| any other `simurg-` prefix, for example `simurg-laravel/` | `sdk` |
| anything else, or no header | `http` |

Official clients MUST send `<client-name>/<version>`, for example
`simurg-cli/1.2.0`.

## Request body

A body is read only for `POST`. The maximum body size is 100 KiB
(102,400 bytes). A larger body gets `413` and no event is emitted.

**JSON body.** If `Content-Type` is `application/json` (parameters such as
`charset` allowed) and the body parses as a JSON object, the receiver reads
two fields and ignores the rest:

- `metrics`: an object of metric name → number. Names MUST match
  `^[a-z0-9_.]{1,64}$` and values MUST be finite JSON numbers. Entries that
  do not match are dropped; the ping is still accepted.
- `output`: a string, handled like a text body.

**Text body.** Any other body, including a JSON body that does not parse as
an object, is treated as text output.

**Output tail.** Output is kept as its last 10 KiB (10,240 bytes). The cut
falls on a UTF-8 character boundary, so the kept part may be slightly
shorter. Invalid UTF-8 sequences are replaced with U+FFFD. When output was
cut, the event has `output_truncated: true`.

**Reserved metric names.** Names starting with `sys.` (resource usage) and
`simurg.` (client overhead) are reserved for official clients. The receiver
does not reject them; the event carries `source`, and the event consumer
decides how to treat them.

## Responses

The receiver validates, emits the event and responds. It never waits for the
event consumer.

| Status | When | Body (`text/plain; charset=utf-8`) |
| --- | --- | --- |
| `200` | Ping accepted. | `OK\n`, or for `start` the run ID followed by `\n`. |
| `400` | Malformed path, exit code out of range, malformed `rid` or `Idempotency-Key`. | A short reason. |
| `405` | Method other than `GET`, `HEAD`, `POST`. | A short reason. |
| `413` | Body larger than 100 KiB. | A short reason. |
| `429` | Rate limit exceeded. The ping is dropped. | A short reason. |
| `503` | The receiver could not hand the event on. The client MAY retry with the same `Idempotency-Key`. | A short reason. |

A `start` response always carries the `Run-Id` header. `HEAD` responses carry
headers only, so for `HEAD` the header is the only place the run ID appears.

A well-formed ping for a token or project key the receiver does not know is
still answered with `200`. The event is emitted with `unverified: true` and
the event consumer verifies the monitor. The receiver MUST NOT answer `404`
for an unknown monitor.

## Rate limits

- At most 60 pings per minute per monitor. Above that the receiver answers
  `429` and drops the ping; the monitor's state does not change.
- Pings the receiver cannot match to a known monitor are additionally limited
  per client IP address.

## Event

For every accepted ping the receiver emits exactly one event, a JSON object.
Pings answered with a status other than `200` emit no event.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `v` | integer | yes | Event schema version. Always `1` in this version. |
| `id` | string (ULID) | yes | Unique event ID, generated by the receiver. |
| `kind` | string | yes | `start`, `success`, `fail` or `exit`. |
| `received_at` | string | yes | Arrival time at the receiver, RFC 3339 in UTC with millisecond precision, for example `2026-10-15T09:00:00.123Z`. |
| `monitor` | object | yes | How the monitor was addressed; see below. |
| `run_id` | string (ULID) or null | yes | For `start`, the new run's ID. For finish pings, the `rid` value or `null`. |
| `exit_code` | integer or null | yes | 0–255 for `exit`, otherwise `null`. |
| `unverified` | boolean | yes | `true` if the receiver could not confirm the monitor exists. |
| `source` | string | yes | `cli`, `sdk` or `http`. |
| `idempotency_key` | string or null | yes | The `Idempotency-Key` header, or `null`. |
| `metrics` | object | yes | Metric name → number. Empty object when there are none. |
| `output` | string or null | yes | Output tail, or `null` when there was no output. |
| `output_truncated` | boolean | yes | `true` if output was cut to the last 10 KiB. |

`monitor` has one of two shapes:

```json
{ "token": "abcdefghijklmnopqrstuvwxyz" }
```

```json
{ "project_key": "pk_abcdefghijklmnopqrstuvwxyz", "slug": "nightly-backup", "create": false }
```

Consumers MUST ignore fields they do not know. New optional fields may be
added within version 1; existing fields never change meaning.

## Run semantics

The event consumer applies these rules. They are part of the contract so
that every client and server agrees on what a ping means.

1. **Overlapping runs.** Every `start` opens a separate run. The number of
   concurrent runs per monitor is limited by the server; exceeding the limit
   produces a warning, not a rejected ping.
2. **Matching finish pings.** A finish ping with `rid` closes that run. A
   finish ping without `rid` closes the most recent open run; if no run is
   open, it records a run that has no start.
3. **Late ping.** A success ping that arrives after the grace period ends
   still marks the monitor up and closes the incident as completed late.
4. **Early ping.** A ping that arrives before the expected time satisfies
   that period; the next due time is computed from the schedule.
5. **Time zones and DST.** Every monitor has an IANA time zone. A skipped
   local hour (clocks forward) does not make the server wait for that run; a
   repeated local hour (clocks back) expects a single run.
6. **Clock skew.** Decisions use `received_at`. Client clocks are never
   trusted, and clients MUST NOT send timestamps that override it.
7. **Exit codes.** Exit code 0 is a success, 1–255 a failure. Exit code 137
   (128 + SIGKILL) MAY be reported as a likely out-of-memory kill.

## Examples

Tokens and keys below are fake. `id` and `received_at` vary per event; the
values shown are placeholders.

### Start

```http
GET /ping/abcdefghijklmnopqrstuvwxyz/start HTTP/1.1
User-Agent: curl/8.10.1
```

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Run-Id: 01JA2B3C4D5E6F7G8H9JKMNPQR

01JA2B3C4D5E6F7G8H9JKMNPQR
```

```json
{
  "v": 1, "id": "01JA2B3C4D5E6F7G8H9JKMNPQS", "kind": "start",
  "received_at": "2026-10-15T09:00:00.123Z",
  "monitor": { "token": "abcdefghijklmnopqrstuvwxyz" },
  "run_id": "01JA2B3C4D5E6F7G8H9JKMNPQR", "exit_code": null,
  "unverified": false, "source": "http", "idempotency_key": null,
  "metrics": {}, "output": null, "output_truncated": false
}
```

### Success

```http
GET /ping/abcdefghijklmnopqrstuvwxyz?rid=01JA2B3C4D5E6F7G8H9JKMNPQR HTTP/1.1
```

Response `200` with body `OK\n`. Event: `kind: "success"`,
`run_id: "01JA2B3C4D5E6F7G8H9JKMNPQR"`, other fields as in the start example.

### Fail

```http
HEAD /ping/pk_abcdefghijklmnopqrstuvwxyz/nightly-backup/fail?create=1 HTTP/1.1
User-Agent: simurg-laravel/0.1.0
```

Response `200` with no body. Event: `kind: "fail"`, `run_id: null`,
`source: "sdk"`, `monitor` in the slug shape with `create: true`.

### Exit code

```http
GET /ping/abcdefghijklmnopqrstuvwxyz/137 HTTP/1.1
```

Response `200`. Event: `kind: "exit"`, `exit_code: 137`. A path ending in
`/256` or `/007` gets `400` and emits no event.

### POST body with metrics

```http
POST /ping/abcdefghijklmnopqrstuvwxyz HTTP/1.1
User-Agent: simurg-cli/0.1.0
Content-Type: application/json
Idempotency-Key: 3f2c9a7e-retry-safe

{"metrics": {"processed": 1240, "errors": 0, "sys.max_rss_kb": 51200, "Bad Name": 1},
 "output": "done\n"}
```

Response `200` with body `OK\n`. Event: `kind: "success"`, `source: "cli"`,
`idempotency_key: "3f2c9a7e-retry-safe"`,
`metrics: {"processed": 1240, "errors": 0, "sys.max_rss_kb": 51200}`
(`Bad Name` is dropped), `output: "done\n"`, `output_truncated: false`.
